# Exports, Types, README, Semver

Your wrapper works. Now make it a package a stranger can install and trust — which is three decisions: what you export, what you promise about changes, and what the README says.

## The exports map

In `package.json`:

```json
{
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" }
  },
  "files": ["dist"],
  "peerDependencies": { "@solana/kit": ">=7 <8" }
}
```

Two things carry weight. `"types"` must be listed **first** in each condition — resolvers read the map in order, and a `types` entry after `import` is silently skipped, so consumers get your code with no type hints. And `@solana/kit` is a **peer** dependency, not a hard one: your client and the consumer's app must share one Kit instance, and a hard dependency would install a second copy. The range `>=7 <8` is a bet you are making on purpose — Kit went 1.0 to 7.0 in about eighteen months, so pinning a single version would strand consumers on the day they upgrade.

## The semver policy you write down

A client whose IDL will change needs a rule its consumers can rely on. This is the one you commit to and are held to at publish time:

- **New instruction** → **minor**. Existing callers are untouched; new capability is additive.
- **Removed field, changed account layout, or renamed export** → **major**. Something a caller depended on is gone or moved.
- **Regenerating against an unchanged IDL** → **patch**. The interface is identical; only the generated bytes were refreshed.

The subtlety the exercise drills: **the most breaking change wins.** A release that both adds an instruction *and* changes an account layout is a **major**, not a minor — you check for breakage before you check for additions, or an added instruction masks a layout change and a consumer's build breaks on what you called a minor bump.

## README minimum

A README a stranger can install from has: the install line, a ten-line `deposit` example that actually compiles, the program id and cluster, and the supported Kit range. Undated and unpinned is exactly how every competitor's material rotted — so state the versions.

## The exercise

`classifyChange` receives four pipe-joined descriptors — the instruction names and account fields before and after a change — and returns `'major'`, `'minor'` or `'patch'`. Every branch you need is already in the starter, but they are in the wrong order and one decoy is mixed in. Order them so the most breaking change is decided first.
